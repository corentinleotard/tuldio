Tuldio — Onboarding v4

Screen 1

Landing — Lien de prospection (seule page publique)

Le prospect clique le magic link. Le JWT est decode cote frontend pour afficher les infos. Au clic "Commencer" → POST /auth/invite → cree user+team → retourne les memes cookies que le login OTP classique.

Token = JWT signe ~500 chars — cache derriere le texte du lien. Valide 30 jours. Pas single-use.
Multi-clic : 1er clic → cree compte, stocke invite_accounts(token_hash, user_id, expires_at). Clics suivants (meme token, <30j) → retrouve le meme user, set cookies frais. Apres 30j → expire. Si email lie → login OTP. Sinon → compte perdu (acceptable).
Forwarding OK : si le prospect forward l'email, l'assistant cree le compte, le prospect clique apres → meme compte. Pas de conflit.
Landing = frontend-only : decode le JWT sans appeler le backend. Verification (signature + expiry + lookup) au POST /auth/invite.
Apres "Commencer" : standard tuldio_access + tuldio_refresh cookies. Meme middleware auth.

Screen 6

Flow complet

Parcours Token
1
Email prospection
Magic link = JWT signe (donnees scrapees, exp 30j). Pas single-use — multi-clic OK.
2
Landing publique (seule page publique)
Frontend decode le JWT. Affiche nom/adresse/tel. Pas de call backend.
3
"Commencer" → POST /auth/invite
Verifie signature + expiry. Lookup invite_accounts : si existe → login user existant. Sinon → cree user + team + seed fields. Retourne AuthResponse + cookies standard.
Token = acces au meme compte pendant 30j. Forwarding OK, multi-device OK. Apres 30j : si email lie → OTP. Sinon → perdu.
4
1er message → Trial 14 jours
Dans POST /api/messages : si subscription_status = null → trial + trial_ends_at = now + 14d.
5
Changement de statut → Modal 3 etapes
E1 : Infos entreprise — champs pre-remplis si donnees scrapees, sinon vides. Pas de skip, toujours affiche pour verification.
E2 : Adresse client + email + OTP (token users) + CGU.
E3 : Resume avec valeurs auto-remplies. Lien "Modifier".
Email collecte ici — devient le login OTP. Pas de skip d'etapes, champs pre-remplis a la place.
6
acceptTerms() → Action executee
POST /teams/me/accept-terms → ensure-legal-defaults. Action originale re-executee.
Parcours Classique (OTP)
1
Login email + OTP
Inchange. Cree user + team si nouveau. Email deja verifie.
2
Chat direct
Plus de redirect /onboarding. Welcome message classique.
3
1er message → Trial 14 jours
Meme logique.
4
Changement de statut → Modal
Meme modal. Pas d'etape email (deja verifie). E1: entreprise. E2: client + CGU. E3: resume.
5
acceptTerms() → Action executee
Identique.
Bilan technique
1 nouvel endpoint : POST /auth/invite
1 petite modif : attacher email a un user existant (OTP verify)
1 nouvelle table : invite_accounts(token_hash, user_id, created_at, expires_at)
Endpoints reutilises : PATCH fields, PUT team, POST document, POST accept-terms, POST otp/send, POST otp/verify

Frontend :
• Page /invite/:token (decode JWT cote client)
• Supprimer redirect onboarding dans route-guards
• Masquer erreurs TEAM_* dans draft-info-bubble
• Composant CompanyInfoModal (fullscreen mobile, modal desktop)
• Intercepter erreur sur tout changement de statut

Core :
• subscription_status nullable (null = pas de trial)
• check-subscription : null = autorise
• 1er message active trial
